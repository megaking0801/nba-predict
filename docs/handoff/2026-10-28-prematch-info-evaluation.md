# 評估：「得知每場比賽開打前的所有資料」能不能贏（2026-10-28，評估文件，未實作）

## 結論（先看這段）
1. **方向對一半。** 盤口已經吸收公開資訊（fs1 ridge 比盤口差 0.36 MAE，區間 [0.24, 0.48]，見 `2026-10-28-learning-curve.md`；訓練資料翻倍只再降約 0.016）。贏盤口要的不是「資料更多」，而是「比盤口更早或更準地知道某個資訊」，或「盤口某個來源比別的來源慢」。
2. **唯一有機會又便宜的機制是價格落後**：傷兵消息出來之後，某個慢的莊家（台彩是候選）還沒跟上。這可以先用一個小實驗觀察，**不需要下注**。
3. **使用者的條件是硬限制**：台北晚上人工下注＝ET 早上，離開賽 8～13 小時；傷兵與先發多半還沒定案，而價格落後通常只持續分鐘到數小時。若優勢要靠實時盯盤與搶下注，使用者目前的作法**做不到**（見 (d)）。實驗的判斷標準因此包含「落後窗口要夠長，人工來得及」。
4. **前提更正：DB 裡沒有國際盤快照。** 查了正式 DB：`market_lines` 全部 14,732 列 `source='espn'`（`book='espn'`），**`oddsapi` 為 0 列**；workflow 的 `USE_ODDS` 預設 `'0'`。2026-10-24 以後的 ESPN 盤口大約每天一批（約 12～14 UTC），偶有 01:00 UTC 的收盤批。所以訊息裡「10:30／22:30／00:30／02:00 UTC 的國際盤快照」是排程時間，不是已存在的資料；要做 (b) 的實驗，國際盤得**新開資料來源**（需花錢，須使用者同意）。

## (a) 賽前資訊清單與取得時點
時點為一般認知，**本次未逐項查證官方規則**（標「未驗證」），實驗第一階段會用資料量出實際延遲。

| 資訊 | 何時出現（ET） | 我們現在怎麼取得 | 市場是否已反映 |
| :- | :- | :- | :- |
| 傷兵報告（官方，隊伍提交） | 賽前一天傍晚首版、比賽日午後更新、賽前約 1.5 小時最終（未驗證） | ESPN `injuries` endpoint，`injury_reports` 每次抓取 append，含 `reported_at`；每天約 4 次抓取 | 國際盤分鐘級反應；ESPN 顯示盤與台彩未知 |
| 先發名單、不上場名單 | 賽前約 30 分鐘～1.5 小時（未驗證） | box score 結束後才有（`player_game_status`）；賽前沒有 | 開賽前最後的盤口動作主要來自這裡 |
| 球員休息（輪休、背靠背） | 多半賽前一天到當天（未驗證）；有些隊賽前才公告 | 背靠背可由賽程算（已是特徵）；是否輪休沒有資料 | 背靠背賽程公開、已反映；臨時輪休通常是消息而非規律 |
| 教練賽前談話、記者推文 | 不定，常在比賽日早午 | 無 | 速度最快；人工看不到 |
| 場館、旅行、休息天數 | 賽程公布即知 | 已有特徵（ctx、travel、altitude） | 已反映；P4 的實驗也沒贏 |
| 裁判指派 | 賽日上午（未驗證） | box score 後才有（`game_officials`） | 影響很小、大小分略相關 |

「有時間差」的只有前三列中**消息剛出現後的那段時間**；其餘是公開且市場已反映的資訊。

另外兩個資料品質問題，會影響實驗：
- `injury_reports.espn_player_id` 在 2026-10-24 以後的 **1,552 列全是 NULL**（實查），只能用 `team_abbr + player_name` 追蹤同一個人。`snapshot_injuries.py` 的 `_player_id` 從 `athlete["id"]` 取值，payload 結構疑似不同；**未查原因，未修**。
- 狀態只有 `Out`（1,207 列）與 `Day-To-Day`（345 列），沒有 Questionable／Probable 之分。
- `reported_at` 是 ESPN 說的條目更新時間，`captured_at` 是我們抓的時間；兩者差的中位數 27.5 小時（p10 3.5 小時、p90 635 小時），因為同一條目每次抓取都重複 append。**這不是「ESPN 比官方慢多少」，不能拿來當延遲。** 要量延遲，必須記每個（隊、球員、狀態）第一次被看到的時間。

## (b) 價格落後：資料收集＋觀察實驗

### 要回答的問題
一個關鍵球員被報 Out 之後，目標盤口（先用 ESPN 盤口當代理，之後才是台彩）多久追上國際盤共識線？追上之前，兩者差幾分？

### 事前登記（資料收集前凍結）
- **事件**：（隊、球員）的狀態第一次變成 `Out`（含 `Day-To-Day`→`Out`），且該隊在 1～14 小時後有比賽。球員為「關鍵」＝事件當下，該隊近 10 場上場分鐘的前 7 名（只用事件前的資料）。
- **參考線**：事件後 60 分鐘的國際盤共識線（至少 3 家的中位數）。
- **落後**：目標線與參考線差 ≥ 1.0 分。
- **主指標**：事件後 15 分鐘仍落後的比例 p，以及落後事件的差距中位數。
- **次指標**：落後事件中，若在事件後 15 分鐘按目標線買「落後那一邊」，相對收盤線的 CLV（以分數計）。**不用輸贏評估**（樣本不夠）。
- **進入第二階段（台彩手動抽樣）的條件，全部要成立**：(1) p 的 95% 單邊 Wilson 下界 > 10%；(2) 落後事件的差距中位數 ≥ 1.5 分；(3) 落後的持續時間中位數 ≥ 60 分鐘（人工要來得及）。任一不成立就停，結論＝沒有可利用的價格落後。
- 1.5 分的由來：若台彩讓分賠率約 1.75（`2026-10-28-takeover.md` 的估計值，未實測），損益兩平勝率 1/1.75 ＝ 57.1%，比 −110 的 52.4% 高 4.7 個百分點；NBA 分差標準差約 12.5（假設常態）→ 1 分約 3.2 個百分點，所以需要約 1.5 分的優勢才打平抽水。

### 要收什麼
1. **傷兵事件**（新表 `injury_events`，只在狀態變化時 insert）：`first_seen_at`、隊、球員名、狀態、detail、ESPN `reported_at`。來源 ESPN `injuries` endpoint，**每 5 分鐘**抓，只在 ET 10:00 到最晚開賽那段。
2. **國際盤線**：Odds API（`spreads`，美／歐盤），事件觸發式：偵測到關鍵球員事件後，在 T0、+5、+15、+30、+60 分鐘各抓一次；加上每場開賽前 30 分鐘的收盤線一次。
3. **ESPN 盤口**：沿用現有 `market_lines`，事件窗口內提高到同樣的時點。
4. **台彩**：第一階段不收（見下）。

### 多久、多少樣本
- 現有資料粗估事件量：2026-10-25 以後有 37 個（隊、球員）從非 Out 變 Out，約每天 10 個，但包含非主力，且現在每天只抓約 4 次，偵測時間很粗。關鍵球員假設佔三分之一，約每天 3 個（**假設**，第一週用真實資料校正）。
- 檢定 H0: p ≤ 0.10 vs H1: p ≥ 0.30，α＝0.05 單邊、檢定力 80%：常態近似約需 20 個事件。為了把 p 估到 ±15 個百分點，目標 **60 個關鍵事件**，約 **3 週**（賽季中）。差距中位數、持續時間的估計也靠這 60 個。
- 第一週只跑偵測（不抓國際盤），先量真實的事件率與 `first_seen_at` 解析度，再決定要不要付 Odds API 的錢。

### 成本（要使用者決定）
- Odds API 額度：事件觸發式約每事件 6 次呼叫；每日約 3 個關鍵事件 → 約 18 次。若 2 個 region × 1 market 各算 2 個點數，約每月 1,100 點。**方案與點數規則未查證**，免費額度夠不夠要看實際方案；超出就是**花錢，須使用者同意**。
- 排程：GitHub Actions 的排程在此 repo 實測晚 3～4 小時（見 CLAUDE.md），5 分鐘輪詢不可行。要用使用者自己的機器、小型雲端 VM 之類的另一種執行環境；這也是額外成本與維運。

### 條款與界線
- **Jbot**（依 `jobs/jbot.py` 開頭所記，2026-10-26 主線讀過，本次未重新驗證）：呼叫間隔 ≥ 5 秒、試用金鑰每天 20 次且全體共用、只有最近 30 天、**禁止自動重複**、僅供研究分析。→ **不能拿 Jbot 做定時或事件觸發的快照**；它只適合使用者手動、一次性的比對。
- **台彩網站**：官網對無瀏覽器請求回 Cloudflare 403；**不繞過**（使用者已同意先不用）。網站條款我**未讀、未驗證**；以排程重複讀頁面是否允許不明，**保守起見不做**。第二階段若要台彩資料，只做「使用者自己打開頁面時手動記錄」，每個事件記一兩個時點，目標 ≥ 20 個事件，只當驗證用。
- ESPN 的 `injuries` 與 scoreboard 是現有程式已在用的公開 JSON endpoint；5 分鐘一次的頻率遠高於現在（每天約 4 次），條款與是否會被限流**未驗證**，先用低頻試跑。
- 這個實驗不下注、不寫入既有表（`injury_events` 是新表，schema 變更按規定只做可重複執行的 `CREATE TABLE IF NOT EXISTS`），不動 workflow；任何寫正式 DB 或新增排程都要使用者當下同意。

### 這個實驗不能證明什麼
- 用 ESPN 盤口當代理，**不等於台彩**。ESPN 盤口若很快跟上，只代表 ESPN 的來源快，不代表台彩快；ESPN 若很慢，也只是指出「慢的來源確實存在」，要不要押台彩還得走第二階段。
- 台彩有自己的開賣與停賣時間、單注上限（未驗證），落後窗口可能根本不在可下注時間內。

## (c) 無法評估的方向
- **球員 props**：DB 沒有任何球員盤口，也沒有莊家的 props 賠率歷史。無法評估。
- **半場盤、單節盤**：只有全場讓分與大小分；沒有半場盤口，也沒有分節的比分資料可對照。無法評估。
- **即時（場中）盤**：資料型態不同（`blob.sportslottery.com.tw/.../On.json` 只有場中盤），且需要毫秒～秒級的決策，與使用者條件無關。不評估。

## (d) 使用者條件的限制（請照實寫進決策）
- 使用者在台北晚上看網站，約 21:00 ＝ ET 早上（夏令時間 09:00，之後 08:00），距離多數比賽（ET 19:00～22:30）8～13 小時。
- 最後的傷兵與先發資訊多半出現在 ET 傍晚，對應台北清晨（約 05:00～09:00），使用者通常在睡覺。即使有價格落後，**搶消息並下注這件事，人工做不到**。
- 使用者晚上能看到的，是「早上已公開」的資訊，而它們多半已被國際盤吸收；能剩下的只有「台彩自己更新慢、整個白天都沒追上」這一種情況，需要落後窗口以**小時**計。這正是上面條件 (3) 要檢驗的。
- 若第一階段顯示落後窗口只有分鐘級，結論就是：**這個方向對台北晚上人工下注的使用者沒有可執行的優勢**，不論資料收集得多完整。要實時盯盤並自動下注是另一個專案，牽涉台彩的下注介面與條款，不在本評估範圍，也不建議在沒有明確授權與條款確認的情況下碰。
- 上面所有數字不改變本專案的立場：模型為娛樂與數據預測，不是投注建議；`playbook` 的玩法回測目前沒有任何玩法賺錢。

## 建議的下一步（由使用者／主線決定）
1. 先做零成本的一步：修／查 `espn_player_id` 為何全是 NULL，並讓傷兵抓取記錄「第一次看到」的時間（新表或 view），照現有頻率跑一週，量真實的事件率。
2. 事件率夠（≥ 2 個關鍵事件／天）再決定是否付 Odds API 與另一個排程環境。
3. 第一階段結果出來前，不申請 Jbot 金鑰、不碰台彩頁面。
