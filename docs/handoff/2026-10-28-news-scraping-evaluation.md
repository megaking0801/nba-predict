# 評估：每小時爬全網新聞／論壇／社群，做第一手資訊差（2026-10-28，唯讀）

使用者的想法：寫腳本每小時爬新聞、論壇、社群裡關於明天賽事的任何消息，過濾後取得「第一手資訊差」。
本文是評估，不是實作。只用 WebSearch／WebFetch 讀說明與定價，**沒有抓取任何網站的實際資料**，也沒有測試任何防護。
網路資料多為第三方網站（標示處已註明），價格與政策會變；WebFetch 內容經小模型摘要。

## 結論（先看這段）
1. **每小時輪詢比「爆料→盤口調整」慢兩個數量級以上。** 業界說法是新聞到盤口調整以「秒」計（來源品質弱，見 (a)）；每小時輪詢的平均偵測延遲就是 30 分鐘，再加上發布到被爬到的延遲。用這種方式搶在**一般莊家**前面，不可能。
2. **能存在的資訊差只有一種：某個慢的莊家（例如台彩）整段時間都沒跟上。** 這種情況下，不需要爬全世界，官方傷兵報告（15 分鐘一份）加一個國際盤 API 就能偵測；多爬社群只是把偵測時間提早，而人工下注的瓶頸不在偵測，在使用者（台北晚上＝ET 早上）。
3. **多數「第一手」來源要錢或正在關閉：** X 沒有免費讀取（每則貼文約 $0.005）；Reddit 依第三方報導，已宣布 2026-10-31 起不再受理新的公開 API 申請、11-13 關 RSS、2027-03 關舊 API。條款允許的免費來源，剛好都是慢的那種。
4. **我的看法與主線的先驗一致：產生可驗證資訊差的機率很低。** 主觀判斷（不是算出來的）：對「台北晚上人工下注」這個使用者，低於 5%。建議**不建置全網爬蟲**；先做已設計好的價格落後實驗（`2026-10-28-injury-events-design.md`），那個實驗若找不到 ≥ 1 小時的落後窗口，爬更多新聞也救不了。

## (a) 可行性與時效
| 來源類型 | 時效（發布 → 可取得） | 本次證據 |
| :- | :- | :- |
| 記者爆料（X 上的 Shams 類） | 通常比官方早數分鐘到數小時（一般認知，**未驗證**） | 搜尋結果只確認 ESPN 傷兵頁把 Shams 列為多筆 2025-26 更新的出處，沒有時效比較 |
| 球隊官方帳號／聲明 | 與官方同時或略早 | 無 |
| 官方傷兵報告 | 每 15 分鐘一份（官方頁面）；前一天當地 17:00 前、比賽日 11:00～13:00（下午 5 點前開賽者 08:00～10:00）提交 | 官方頁面（本次讀過，見來源調查） |
| Reddit r/nba | 多為轉貼，晚於原始來源（一般認知，**未驗證**） | 搜尋沒找到任何 Reddit 與 X 的時效比較 |
| 新聞 RSS／聚合 | 晚於原始來源數分鐘到數小時，視網站而定 | 無 |
| ESPN 傷兵 endpoint（本專案） | 我們的 `reported_at` 是 ESPN 條目更新時間 | 見下 |

**盤口多快反映：**
- 唯一找到的說法來自 Action Network 的教學文章：消息出現到盤口調整「以秒計，不是分鐘」，可信消息出現時莊家常先「circle」（暫時下架）再改價；另一篇稱盤口有時在消息公開前就動（銳利資金）。**這些是業界文章，沒有數據**，搜尋沒有找到任何量測 NBA 傷兵消息到盤口調整時間的研究。
- **我們自己的資料量不到。** 查正式 DB：2026-10-24 以後，「Out 條目 × 該隊 36 小時內下一場」共 119 組；其中 **0 組**在 `reported_at` 前後 3 小時內有 ≥ 2 筆盤口快照，100 組完全沒有快照，只有 5 組在前後 12 小時內看到讓分數字不同。原因是 ESPN 盤口每天只抓約一批。所以「`reported_at` 對盤口快照」目前**無法**回答反應時間，這也是第一階段要提高解析度的原因。
- 從 `reported_at` 到開賽的時間中位數 **8.3 小時**（p10 1.1 小時、p90 27.7 小時），代表多數傷兵消息在開賽前半天就有了。

**每小時輪詢夠不夠快：** 不夠。偵測延遲平均 30 分鐘（最壞 60 分鐘）；若盤口以秒到分鐘計，等我們看到消息時，線早就動完了。就算改成 5 分鐘輪詢，對一般莊家仍太慢。
**使用者的下注時點是另一層延遲：** 使用者在台北約 21:00＝ET 09:00（夏令；冬令 08:00）。此刻比賽日官方報告（當地 11:00～13:00）多半還沒出，使用者看到的是前一天傍晚的版本，距離開賽約 8～13 小時。在使用者看網站之後才出現的消息，他當下不可能行動；在這之前出現的消息，市場已經消化數小時。

## (b) 合法與條款
**不得繞過登入、付費牆、Cloudflare 或其他防護；以下全部以此為前提。**
| 來源 | 費用／可用性 | 條款 |
| :- | :- | :- |
| X API | 依 docs.x.com：貼文讀取 **$0.005／則**（以回傳筆數計，24 小時內重複請求同一則不重複收費），每月上限 300 萬則；搜尋與串流的單價該頁未列，要看開發者主控台。第三方報導新開發者已無免費層（2026-02-06 起），一次性額度 $70 的說法只有單一來源。**要花錢，須使用者同意** | 開發者條款（儲存、分析、轉存的限制）**未讀** |
| Reddit | 依第三方報導（Reddit 自己的條款頁 WebFetch 無法連線，**未讀**）：2026-09-30 宣布，**2026-10-31 停止受理新的公開 API 申請**（三天後）、**11-13 關閉 RSS**、2027-03 關舊 API；免費層限「已核准的非商業」用途，新申請需人工核准約 2～4 週；指向 Devvit（版主工具）。資料以第三方二手報導為主 | 不得用 HTML 爬取來繞過 API（以防護為由也不行）。**結論：不可行** |
| 新聞網站（ESPN、Yahoo、CBS、The Athletic 等） | 多數無公開 API | robots.txt 與各站條款我**沒有逐站讀**，不能說「允許」。已讀的：Disney（ESPN）禁止用 robot／script 自動存取與蒐集資料；NBA.com RSS 僅供個人非商業（搜尋摘要），NBA.com 使用條款限個人非商業並禁止賭博相關使用統計（見來源調查） |
| RSS | 網站主動提供的訂閱，一般認為比爬網頁風險低，但**是否允許自動化輪詢、儲存、做賭盤分析仍看各站條款**（未讀） | 同上 |
| 社群貼文（Instagram、Threads、Telegram 頻道等） | 多無免費 API | 未讀；爬取通常違反條款 |

簡言之：**條款清楚允許、又免費、又夠快的「第一手」來源，目前沒有找到。** 夠快的（X）要錢，免費的（RSS、官方報告）慢或有條款疑慮。

## (c) 過濾方法與成本
流程（若真要做）：
1. **收集**：只用條款允許的來源；記錄來源給的**發布時間**（不是我們抓取時間，因為每小時輪詢會把事件系統性地往後拖）。
2. **去重**：URL 與標題正規化雜湊；近似重複用 simhash；事件以（隊、球員、狀態）聚合，事件時間＝群組中最早的發布時間。
3. **實體比對**：30 隊名稱與別名、現役球員（`roster_snapshots` 約 500 人）；名字比對要處理暱稱、同姓與縮寫。
4. **關鍵詞預篩**：out／ruled out／questionable／doubtful／will not play／rest／load management／return／starting lineup 等。
5. **LLM 分類**（只處理過了 3、4 的少數）：輸出 JSON——隊、球員、主張類型（狀態變化／先發／交易／其他）、主張的狀態、涉及的比賽日、是否原始報導或轉述、可信度。
6. **可信度**：分層（官方 > 公認記者 > 聚合 > 論壇）；論壇需交叉驗證；事後用官方報告當真值，統計每個來源的命中率。

**成本估算（Claude）：** 假設每天 3,000 則進來、實體比對與關鍵詞後剩 300 則進 LLM，每則約 600 輸入＋100 輸出 token，即每天約 18 萬輸入、3 萬輸出 token。單價各家第三方頁面互相矛盾（Haiku 4.5 約 $1／$5 每百萬 token，Haiku 5.5 有頁面寫 $0.10／$0.50；**都不是 Anthropic 官方價目頁**），保守用較高的：約 **$0.33／天**（約 $10／月）；較低的則約 $0.03／天。就算不預篩、3,000 則全送，也是每天 $0.3～$3.3。**LLM 費用不是瓶頸；來源取得與時效才是。** 延遲：每則約 1～3 秒，對每小時批次完全不是問題。

## (d) 可驗證的小實驗（不花錢的版本）
**問題：** 對同一個傷兵事件，我們的偵測時間比盤口反應早或晚多少？

**事件與時間點（每個事件記）：**
- `t_news`：最早的相關消息發布時間（來源給的）。
- `t_report`：官方報告／ESPN 條目首次出現的時間。
- `t_detect`：我們抓到的時間。
- `t_move`：參考盤口（國際盤共識）第一次與事件前讓分相差 ≥ 0.5 分的快照時間。
- 主指標：`t_move − t_detect`（正值＝我們比盤口早）；另加 Odds API 各家莊家 `last_update` 的差（誰先改價、慢多少），每家的 `last_update` 與我們的抓取時間都要記；次指標：事件後 15／60 分鐘仍落後 ≥ 1 分的比例。

**資料：** 2 週內所有關鍵球員（近 10 場分鐘前 7 名）的狀態事件。盤口取樣用 The Odds API 免費層（一次呼叫 1 點、回全部比賽），事件觸發式在 T0、+5、+15、+30、+60 分鐘各 1 次，約每事件 5 點；60 個事件約 300 點，在 500 點／月內。
**限制，必須先承認：**
- 免費且條款允許的來源**主要是慢的來源**，所以實驗大概只能說「用慢的來源，我們比盤口晚」。這個負面結果**不能**推論到 X 上的記者。
- 每小時輪詢的 `t_detect` 誤差最多 60 分鐘，要量到 5～15 分鐘的差，輪詢必須 ≤ 5 分鐘，這又回到「Actions 排程做不到」的問題（見 `2026-10-28-injury-events-design.md` §0）。
- 以上盤口快照是 5 分鐘解析度，只能判斷「分鐘級」的反應，判斷不了「秒級」。

**事前登記的判斷標準（與價格落後實驗一致）：**
- 事件後 15 分鐘仍落後（≥ 1 分）的比例，95% 單邊 Wilson 下界 > 10%；
- 落後事件的差距中位數：≥ 1.5 分＝對國際盤有意義；≥ 2.5 分且持續時間中位數 ≥ 60 分鐘＝對台彩有可能（換算見 `2026-10-28-prematch-info-evaluation.md`：台彩約 1.75 的兩平勝率 57.1% ≈ 2.2 分）；
- 落後持續時間中位數 ≥ 60 分鐘。
全部成立才進入下一階段；任一不成立就結束。

**需要多少樣本：**
- 偵測「落後比例 ≥ 30%」對「≤ 10%」（α＝0.05 單邊、檢定力 80%）：約 20 個事件；偵測「我們比盤口早的事件占 ≥ 10%」對「≤ 2%」：約 36 個事件。
- 估計「領先時間」的中位數到 ±15 分鐘（假設標準差 60 分鐘）：約 60 個事件。
- 取 **60 個關鍵事件**。以每天約 3 個關鍵事件（**假設**，第一週用真實資料校正）算，約 **3 週**；2 週只會到約 40 個，勉強。
- 若要證明「全網爬蟲比官方報告多出領先時間」，需要「新聞早於官方」的事件（假設 20%）至少 60 個，即總事件約 300 個，約 **10 週**——不現實，這也是我建議跳過的理由。

## (e) 誠實結論與建議
- **看法：** 同意主線的先驗，機率很低（主觀 <5%，不是計算結果）。理由：(1) 莊家與職業玩家盯的是同一批來源，且延遲以秒計，還付費買專業資料；(2) 每小時輪詢不可能比秒級快；(3) 使用者人工、台北晚上，行動延遲以小時計；(4) 真正快的來源（X）要錢，免費且合規的來源慢；Reddit 正在關閉；(5) 唯一的結構性機會是慢的莊家，那不需要全網爬蟲。
- **可能的反例（我沒有證據）：** 冷門消息（地方記者、非英語媒體）可能不會立刻傳到莊家，但大莊家也有人專職盯這類來源，且我們沒有證據顯示台彩會對這類消息更慢反應。
- **建議順序：**
  1. 先做價格落後實驗的階段 0（本機輪詢、不寫 DB、不花錢）與 Odds API 免費層的少量取樣，看慢的來源存不存在。
  2. 只有當落後窗口中位數 ≥ 60 分鐘，才值得評估「多一個新聞來源能不能提早偵測」；否則停止，不蓋爬蟲。
  3. 不做：繞過任何登入、付費牆或防護的爬取；不經使用者同意的付費 API（X）。
- **需要使用者決定：** 是否願意付 X API（每則 $0.005，每天監控 30 個帳號、每帳號約 20 則，約 $3／天，**我的估算**）；是否接受 NBA 條款的賭博相關限制（見來源調查）。
