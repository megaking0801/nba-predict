# 台彩賽前盤快照與比價（設計，2026-10-29）

## 1. 目的
使用者在台彩下注，固定在**台北晚上 9 點左右**下注隔天早上的 NBA。模型贏不了盤口（P4／P5／C1 全部負面），所以這裡不靠模型，改問一個市場問題：

> 台北 21:00 的台彩價格，跟接近開賽時的國際盤相比，是否常常有正期望值？特別是國際盤因消息變動、台彩還沒跟上的時候。

做法：定時抓台彩官方賽前盤，以及國際盤（The Odds API 的 Pinnacle 為主、ESPN 的 DraftKings 為輔），累積到 2026-11-30 後只讀分析一次。

## 2. 目標、非目標、反目標
- 目標：每天自動累積快照；一支只讀分析程式算出每場、每個時段「台彩價格對國際公允價的期望值」；累積約 150～200 場後給出「有／沒有」的結論。
- 非目標：不改模型、不改網站、不寫正式 DB、不做下注建議或通知。
- 反目標（即使做得出來也算失敗）：繞過任何防護（Cloudflare、地區限制）；在國外伺服器抓台彩；把台彩或 ESPN 原始資料放進 public 程式 repo；為了得到正結論而事後挑時段、挑盤口（見 §7 預先登記）。

## 3. 已查證的事實（2026-10-29）
- **台彩資料流**：`https://blob3rd.sportslottery.com.tw/apidata/Pre/34765.1-Games.zh.json`（`34765.1` = 籃球，來自使用者提供的 HAR）。台灣 IP 一次普通 GET 回 200、約 108 KB、15 場（含 3 場 `tn = 美國職籃`）。開源專案 `panchiyu1-cloud/sports-analyzer` 用同一資料流，並說明國外 IP 會被 CloudFront 擋。`blob.`（不是 `blob3rd.`）主機回 404。檔案開頭有 UTF-8 BOM。
  - 結構：場次 `{id, no, an 客隊中文全名, hn 主隊中文全名, kt 開賽 "+08:00", tn 聯賽, ms[...]}`；盤口 `{name, mv 線, ss 更新時間 "+08:00", cs[...]}`；選項 `{name, hv 讓分線, pd, pu}`，**賠率 = 1 + pu/pd**（pu、pd 是字串）。
  - 方向與正負號（以 2026-10-29 實際資料核對）：讓分選項 `name` 是「隊名＋該隊的線」，例如 `沙加緬度國王 +5.5`、`紐奧良鵜鶘 -5.5`；同一盤口兩個選項的 `hv` 相同，都是**主隊**的讓分（`-5.5` = 主隊讓 5.5）。大小分選項 `name` 是 `大 237.5`／`小 237.5`，`hv` 是總分線。不讓分選項 `name` 是隊名、`hv` 為空。
  - 盤口名稱實例：`不讓分`、`[總分]讓分 -5.5`（同場同時開 3 條讓分線）、`[總分]大小 237.5`、`<隊名> 大小`（球隊總分）、`[上半場]…`、`[第1節]…`、`得分最高單節`。本設計只用 `不讓分`、`[總分]讓分 …`、`[總分]大小 …`。
  - 每個盤口有欄位 `m`（值 1／2／3）。2026-10-29 樣本：NBA 灰熊 @ 拓荒者全部盤口為 1、另兩場為 2，中國職籃全為 3、WNBA 全為 1。**推測**是「最低過關數」（1 = 可買單場），**未驗證**。
  - 場次有 `er`（例如 `sr:match:73719454`），是 Sportradar 的比賽 id，可輔助配對。
  - 主盤約 1.72／1.72，抽水約 14%（國際盤 -110／-110 約 4.5%）。
- **ESPN 計分板**：`https://site.api.espn.com/apis/site/v2/sports/basketball/nba/scoreboard?dates=YYYYMMDD`（**美東日期**）。不帶 `dates` 時預設是已打完的那天、沒有盤口；**不支援日期區間**（回錯誤）；回應是 gzip，客戶端要解壓。每場 `competitions[0].odds[0]` 有 DraftKings 的 `moneyline / pointSpread / total`，各含 `open` 與 `close`（= 目前）的 `line` 與美式 `odds`。
- **開賽時間**（正式 DB `games_v2`，換成台北時間）：2025-26 例行賽 1,231 場中 89% 在台北 07～11 點開打（08 點最多，32%）；約 6% 在凌晨 01～05 點（美國週末下午場）。2026-11-01 美國結束夏令時間後整體晚 1 小時。
- **現有收盤快照幾乎無效**：最近 10 天 68 場例行賽，28 場開賽前沒有任何 `market_lines` 快照，只有 7 場最後快照在開賽前 3 小時內，中位數約開賽前 9.3 小時（推測是 GitHub 排程延遲 3～4 小時，未查 workflow 紀錄）。所以國際盤收盤要由本設計自己抓，不能依賴 `market_lines`。這個 bug 另案處理，不在本設計範圍。
- 延長賽：網路文章稱台彩籃球**不讓分**含延長賽；**讓分與大小分是否含延長賽未查證**（台彩足球只算正規時間）。DraftKings 的 NBA 讓分與大小分含延長賽。
- 單點觀察（2026-10-29 下午）：3 場台彩的主讓分線與 DraftKings 完全相同，總分相差 0～1 分。台彩平時緊跟國際盤；若有機會，只會在國際盤變動後的空窗。
- iOS 捷徑「特定時間」個人自動化在新版 iOS 可設「立即執行」（Apple 說明）；手機鎖定時某些動作可能卡住，**未在使用者手機上驗證**。
- 台彩網站服務條款：沒找到禁止自動擷取的條文，但官網擋自動化，**沒能核對官方條款頁**。用法：個人研究、每天 7 次、不轉載。

## 5. 手機端（iPhone 捷徑）
- 一個捷徑，每次執行：
  1. 計算美東日期：台北時間 ≥ 12:00 用台北當天，否則用台北前一天，格式 `yyyyMMdd`。
  2. GET 台彩資料流 → 原樣上傳為 `tw_snapshots/<台北日期 yyyyMMdd>/<yyyyMMddTHHmm>+0800-tw.json`。
  3. GET ESPN 計分板（`dates=` 第 1 步的日期）→ 原樣上傳為同資料夾 `<同一時間戳>-espn.json`。
  3b. **06:00 以外的 6 個時段**另外 GET The Odds API `https://api.the-odds-api.com/v4/sports/basketball_nba/odds?apiKey=<key>&bookmakers=pinnacle,draftkings,fanduel&markets=spreads,totals&oddsFormat=decimal` → 上傳為 `<同一時間戳>-oddsapi.json`。每次 2 點（2 種盤口 × 1 個地區，10 家以內莊家算 1 個地區），每月約 360 點，免費方案 500 點（我的決定：跳過 06:00 以留餘裕）。
  4. 上傳方式：GitHub REST `PUT /repos/megaking0801/nba-predict-data/contents/<path>`，body `{"message": "...", "content": <base64>, "branch": "main"}`，標頭 `Authorization: Bearer <token>`、`Accept: application/vnd.github+json`。只新增；同名檔案已存在就失敗、不覆寫。
- 只用普通 GET，不偽造 User-Agent、不帶瀏覽器 cookie。遇到 403 或驗證挑戰就停用並回報，不重試、不換手法。
- 檔名時間戳帶**手機當下的實際時區偏移**（捷徑「格式化日期」自訂格式 `yyyyMMdd'T'HHmmZ`，例如 `20261029T2100+0800`），所以出國時也換算得回 UTC；上傳內容保持原始回應，不另外包一層（實作時的決定，取代原本的兩個選項）。
- 觸發：個人自動化「特定時間 → 立即執行」，時段 **21:00、06:00、07:00、08:00、09:00、10:00、11:00**（台北），共 7 個。11:00 是因為 2026-11-01 之後多數比賽在台北 08～12 點開打（我的決定）。凌晨 01～05 點的場次（約 6%）不抓，接受這個缺口（我的決定）。
- 權杖：GitHub **細粒度個人權杖**，只授權 `nba-predict-data`、權限只有 Contents 讀寫，效期 1 年。權杖只存在手機捷徑裡，不進任何 repo、不貼到對話。
- 上線順序：先建 1 個自動化，**手機鎖定狀態下**實測能跑並在 repo 看到該時段應有的檔案（06:00 兩個，其他時段三個），再複製其餘 6 個。
- 交付：`docs/tw-shortcut-setup.md`（程式 repo）——逐步截圖等級的文字說明（捷徑每個動作、欄位值、權杖建立步驟、如何驗證、如何停用：撤銷權杖或關閉自動化）。

## 6. 電腦端（程式 repo）
- 新模組 `jobs/tw_compare.py`：**主要指標只讀檔案**，不連 DB、不連網、不 import `ensure_schema`；次要損益才用 `connect_readonly()`，且可用參數關掉；沿用 `tests/test_playbook.py::test_module_is_read_only` 的掃描方式加一個同類測試。
- 輸入：`data/tw_snapshots/**`（`data/` 是資料 repo 的 clone）。輸出：報告 JSON（路徑由參數指定），以及終端機摘要。
- 比賽結果（只用於次要的實際損益）：以**只讀連線**從正式 DB `games_v2` 取比分（沿用 `webui.build_site.connect_readonly`，和 `jobs.playbook` 一樣），不寫 DB、不呼叫 `ensure_schema`。主要指標不需要比賽結果（我的決定）。
- 解析：
  - 解析器要先拿**真實快照**核對方向與正負號再定稿：使用者 2026-10-29 的實際台彩檔（session scratchpad 的 `pre_bk.json`）由實作者放進資料 repo 的 `tw_snapshots/_samples/`（private），只在本機用來核對，不進程式 repo。
  - 台彩：去 BOM；只取 `tn == 美國職籃`；`不讓分`、所有 `[總分]讓分 X` 線、`[總分]大小 X`；賠率 = 1 + pu/pd；記錄每個盤口的 `ss`。
  - ESPN：`odds[0]` 的 DraftKings `close`（= 快照當下價格）與 `open`；美式轉小數。
  - 隊名：在 `jobs/teams.py` 新增「中文名稱 → 縮寫」函式（以中文短名做結尾比對），對到 0 個或多於 1 個都 raise；`jobs/jbot.py` 的 `team_abbr_from_cn()` 改用它。ESPN 端縮寫一律經 `normalize_espn_abbr`。
  - 選項方向：以選項 `name` 的隊名判斷主客，並檢查 `name` 裡的正負號與 `hv` 一致，不一致就報錯。
  - ESPN：檢查 `odds[0].provider.name` 是 DraftKings，不是就報錯；處理 `o239.5`、`+100` 這類字串。
  - 配對：（主隊、客隊、開賽時間 ±3 小時），`er` 可輔助。開賽時間以 ESPN event 的 UTC 時間為準；延賽或改期的場次排除並列在報告。
  - 時間：分析一律以 UTC 時間戳與美東比賽日分組，不用資料夾的台北日期。
  - 解析器定稿前，用**捷徑第一次成功上傳的真實快照**（台彩與 ESPN 各一份）人工核對方向、正負號與欄位。
- **參考價**：Pinnacle（The Odds API）優先；沒有 Pinnacle 時用 The Odds API 各家去水機率的中位數（與 `jobs.playbook.market()` 同一做法）；兩者都沒有才用 ESPN 的 DraftKings，並在報告標明每注用的是哪一種。官方註明 Pinnacle 賠率「取自公開網站，可能有延遲」，所以延遲事件以 DraftKings 與 Pinnacle 兩者都移動才算。
- 公允價公式（不可直接用 `jbot.spread_ev()`／`total_ev()`，它們不看國際盤的賠率）：
  1. 參考價兩邊乘法去水，得主隊在參考線 `L_dk` 過盤的公允機率 `p`。
  2. 反推隱含平均分差 `μ = −L_dk + σ·Φ⁻¹(p)`。
  3. 主隊在台彩線 `L_tw` 過盤機率 `= 1 − Φ((−L_tw − μ)/σ)`；總分同理（`σ` 為 `SIGMA_MARGIN = 12.5`、`SIGMA_TOTAL = 19.0`，在 `jobs/jbot.py`）。
  4. 整數線用 ±0.5 連續性校正拆出贏／走／輸機率，`EV = p_贏 × 賠率 + p_走 − 1`。
  5. 測試鎖住：參考價兩邊 -110 時，結果要等於 `jbot.spread_ev`。
- 「收盤」= 該場**開賽前最後一份**有參考價的快照（The Odds API 或 ESPN，依上面的參考價優先順序；不是 `market_lines`），且必須在開賽前 **60 分鐘內**（整點時段保證每場有一份落在這個範圍，除非漏跑）；超過的場次不進主要樣本，只列在報告（我的決定，採 60 分鐘而非加半點時段，避免 13 個自動化）。
- 「21:00 快照」= 檔名時間在台北 20:45～21:30 之間的那一份；沒有就那一天全部不下注，不准用其他時段替代。
- 每場、每個台彩快照時段、每個選項計算 `EV = 公允機率 × 台彩賠率 − 1`，公允機率分兩種：同一時間的參考價、以及收盤的參考價。
- 另外偵測「延遲事件」：兩份相鄰快照之間參考價主線移動 ≥ 1 分（讓分）或 ≥ 1.5 分（總分），而台彩「最接近參考價移動前主線」的那條盤口 `ss` 沒變。
- 每注記錄該盤口的 `m`（疑似最低過關數），報告分 `m = 1` 與 `m ≥ 2` 列出。
- 預先登記的常數（60 分鐘、1／1.5 分、150 注、99%、`block_days=1`、20 個比賽日、分析日期、每週 3 注）寫成模組常數，並用測試鎖住數值。

## 7. 預先登記（避免事後挑結果；開始累積資料後不得修改）
- **分析只做一次**：固定在 **2026-11-30（台北）**，用當天以前的全部快照。之前只報進度，不報顯著性；不得因為中途結果好看而提早下結論，也不得延後（我的決定）。
- **選注只能用 21:00 當下知道的資訊**：每場在 21:00 快照中，用「同一時間的 參考公允價」算台彩讓分與大小分各選項的 EV，取最高的一注；EV ≤ 0 的場次不下注。收盤只用來評分。
- **主要指標**：這些注對**收盤參考價** 的期望值 `EV_close`（業界的 CLV）的平均。不需要比賽結果。
- **判定「有」必須同時滿足**（任一不成立就是「沒有」）：
  1. 注數 ≥ 150，且涵蓋 ≥ 20 個不同美東比賽日；分析日不足就直接判「沒有」——§1 問的是「常常有」，機會少本身就是答案。
  2. 頻率：平均每週 ≥ 3 注。
  3. `jobs.feature_ablation.block_bootstrap_ci(d, block_days=1, level=0.99, reps=10000, seed=0)`（`d` 欄位：`date` = 美東比賽日、`d` = `EV_close`）的下限 > 0。報告同時列每日平均的 t 區間作對照。
  4. **穩健性**：在 σ 敏感度（讓分 11／12.5／14、總分 17／19／21）每一組下限都 > 0；且在「不需換線」子集合（台彩線與 收盤參考主線相差 ≤ 0.5 分）平均 `EV_close` > 0。
- **「有」的意思**：值得進入下一階段的**預先登記前瞻追蹤**（先記帳、可小額），事先寫好停損與停止條件，並換用更準的參考價重新驗證。不代表已證實能獲利；要宣稱能獲利，仍須達到 `jobs.playbook.passes()` 的標準（`MIN_BETS = 1000`、下限 > 0、至少 2/3 球季為正）。目前沒有 21:00 即時計算工具，結論也要寫明「目前無法照著下注」。
- **報告必列**：注數、頻率、按「收盤距開賽時間」分組的 `EV_close`、`m = 1` 與 `m ≥ 2` 分開的結果、兩個對照組（「每場所有讓分與大小分選項隨機選一注，seed 固定」與「主線兩邊平均」，後者應接近 −14%，當健全性檢查）。
- **次要指標（只描述）**：同一批注的實際損益（含整數線走盤），用正式 DB 的比分。
- 其他時段、不讓分、延遲事件都是探索性，只描述、不當結論。
- 單注的 EV 不等於串關的 EV：若某注所在場次 `m ≥ 2`（推測必須串關），另一關的抽水會吃掉優勢，報告要寫明。

## 8. 測試
- 用**合成**的小型 fixture（依 §3 的結構手寫，不放真實台彩資料）：BOM、pu/pd 字串、3 條讓分線、未知隊名報錯、ESPN `open/close` 與美式轉換、日期配對、換線公式、去水、延遲事件判定。
- 解析器以真實樣本（§6）人工核對方向與正負號後才定稿。
- 全部測試 `python -m pytest tests -q` 要過。
