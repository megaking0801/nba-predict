# NBA 預測：總體規劃

日期：2026-10-23
狀態：草稿，待使用者審閱
範圍：這份是總體規劃，不是單一專案的設計。每個專案（第 6 節）開工前，各自另寫設計文件，再寫實作計畫。

## 1. 為什麼要做

使用者在台灣運彩（台彩）下注，最常玩的是**受讓分串 2～3 關**，最常見的虧損原因是串關沒過。
使用者想要的是：每天打開網站，知道今晚每場誰贏、勝率、讓分、大小分，以及**在台彩怎麼買、哪場值得買**。

已向使用者說明並取得共識的事實：
- 「最有把握贏」不等於「最能賺錢」。能不能賺，取決於模型機率是否高於賠率隱含的機率（edge），台彩抽水比國際盤重。
- 串關的過關機率是各關相乘，抽水也逐關疊加；每關的損益兩平門檻不會因為串關而降低。以每關賠率 1.75 為例，每關都要穩定超過約 57.1% 才不虧。
- 深度學習不保證更準；準度主要來自「知道更多」（陣容、傷兵），不是模型更複雜。

## 2. 目標、非目標、反目標

**目標**
- 網站每天針對有優勢的場次，給出「台彩賠率至少要多少才值得買」，由使用者自己對照台彩 App 決定。
- 沒有任何場次達標時，明確顯示「今天不建議」。
- 照推薦下注的長期戰績誠實公開（含輸的）。
- 模型改以「贏市場」為目標：評分看 CLV（與收盤盤口比較）、讓分回測 ROI、機率校準；猜中率只當參考。
- 交易、傷兵能在賽前反映到模型（以「今晚預計上場名單」計算球隊強度）。

**非目標**
- 不自動抓取台彩資料（見 §4.1）。
- 第一版不做 on/off（球員在場／不在場差異），排在最後一個專案。
- 不做即時（比賽中）預測。

**反目標**（技術上可行，但做了就算失敗）
- 推薦被包裝成「穩賺明牌」，或只挑好看的戰績講。
- 回測偷看未來（用到預測當下還不知道的資料，例如收盤後才知道的盤口、賽後才知道的上場名單）。
- 為了讓推薦變多而放寬門檻（CLAUDE.md 已有同樣規則）。
- 用繞過網站防護的方式取得資料。

## 3. 限制

- 遵守 `CLAUDE.md` 全部規則：資料只走 ESPN、時間存 UTC、schema 只做可重複執行的新增式 migration、`market_lines`／`predictions` 只增不改、未經同意不寫正式 DB、不 push、不觸發 workflow。
- 預算：目前全部免費（Supabase 免費方案、GitHub Actions、GitHub Pages）。任何付費方案都要使用者另外決定。
- 不新增需要 Streamlit Cloud 建置的依賴。Parquet 需要的 `pyarrow` 已經是 Streamlit 的依賴（已驗證：`pip show streamlit` 的 Requires 含 `pyarrow`，本機版本 24.0.0）。
- 執行環境：GitHub Actions 在美國，stats.nba.com、cdn.nba.com 會擋；ESPN 可用。

## 4. 已確認的事實（2026-10-23 調查）

### 4.1 台彩賠率
- 台彩官網前面有 Cloudflare 機器人驗證。以未做任何偽裝的 Playwright 實測一次：回 `403`，頁面為 Cloudflare Turnstile 驗證頁，看不到賠率。
- **決定**：不做規避驗證的抓取。第一版網站只算「最低可接受賠率」，使用者自己對照台彩。
- 備案：第三方 Jbot API（sportsbot.tech）提供台彩 NBA 賠率（初盤、尾盤、變動），訂閱 1,000 元／月；條款限「學術研究、數據分析」，是否可公開顯示未說明；免費試用禁止排程。暫不採用，留待使用者決定。

### 4.2 資料庫（Supabase，唯讀查詢）
- 使用中的是 **Project2（project ref 以 `rzei` 開頭，ap-northeast-1）**：依據是 `.streamlit/secrets.toml` 只含這個 ID（使用者自己執行 grep 確認）。完整 ref 不寫進公開 repo，在 Supabase 後台或本機 MCP 設定裡查。GitHub Actions secrets 指向哪個專案見 §6 P1。
- Project1（project ref 以 `vciz` 開頭）內容未知，**不要動**，確認無用後再由使用者決定是否刪除。
- Project2 曾因閒置被暫停，2026-10-22 19:34 UTC 由使用者恢復。免費方案一週無活動會再暫停。
- 資料庫大小 40 MB（上限 500 MB）；最大表 `player_game_stats` 22 MB、約 9.06 萬列（估計值）。
- 比賽：2023-24、2024-25、2025-26 三季，例行賽每季 1,231 場（比正常 1,230 多 1 場，原因**未驗證**，推測是 NBA 盃冠軍戰），全部已完賽，最後一場 2026-06-13。
- 球隊 box score 缺漏（以列數除以 2 估算）：2023-24 約 18 場、2024-25 約 3 場、2025-26 無。
- 盤口：只有 ESPN，每場一筆（2024-25 例行賽缺 1 場）。`captured_at` 全部剛好等於開賽時間，是回補時人為填入，**不知道是開盤、收盤或中間的盤**。
- 傷兵快照：只有 2026-06-17 到 2026-08-19（休賽期）。**球季中的傷兵資料完全沒有**。
- 預測：2,938 筆，`predicted_at` 全部是 2026-06-18 同一時刻（一次批次回填）。
- 上線中的模型：
  - `margin_model` 2026.06.18-r1：猜勝負 67.3%（n=2,938），讓分回測報告為空（`n_picks: 0`）。
  - `total_model` 2026.06.20-r1：大小分方向 48.1%（n=2,609），校準斜率 −0.12，Brier 0.267，比直接相信盤口（0.250）差。
  - `over_calibrator` 2026.06.20-r1 為啟用狀態，但 `trained_rows` 是 0（原因未查）。
- 8 月 3、10、17 日的重新訓練版本都未啟用（原因未查）。這些版本使用同樣的 3,738 列訓練資料，其 walk-forward 讓分回測：命中 50.2%、ROI −3.8%（n=1,433，-110 賠率的損益兩平是 52.4%）。**這套方法目前在讓分盤贏不了盤口。**

### 4.3 ESPN 公開 API（`site.api.espn.com`）
抽樣驗證（每個日期抽 1 場，所以代表「有這個欄位」，不代表每場都有）：
- 有：裁判（2016、2020、2026）、逐回合紀錄與出手座標（2016 全部出手都有座標，2020、2026 約八成）、先發 `starter`、`didNotPlay` 與原因（例如 2020 年 Lillard「RIGHT GROIN STRAIN」）、換人文字（如「X enters the game for Y」）、球隊名單 API `teams/{id}/roster`（含傷病狀態）。
- 比賽頁的 `injuries` 是**當下**的傷兵名單，不是歷史（2016 的比賽列出 2025 年新秀），不能當歷史資料。
- 逐回合紀錄沒有直接標示場上五人，on/off 需要從先發與換人紀錄自行推算。
- 盤口（`pickcenter`）：2016–2023 抽樣有共識讓分（2016 那場無總分）；**2024、2025 抽樣的場次沒有盤口**；2026 有 DraftKings 開盤與收盤。

### 4.4 儲存
- Firebase 不採用：整個資料層是 Postgres SQL（JOIN、view、評估查詢），換過去等於重寫。
- 維持 Supabase 免費方案；回補十一季的 box score 估計總量約 120 MB，放得下。
- 逐回合原始資料**不進資料庫**，存成 Parquet 檔；位置在專案 P2 決定（候選：Cloudflare R2，或在 Actions 內處理完即丟、只保留結果）。不放公開 repo 的 Release（重新散布 ESPN 資料有條款風險）。

## 5. 已定案的決定

| 項目 | 決定 |
| :- | :- |
| 網站推薦形式 | 每場「台彩至少要多少賠率才值得買」＋「今天不建議」＋誠實戰績；串關只從有優勢的場次組，顯示真實過關機率 |
| 台彩資料 | 不抓；使用者自己對照 |
| 模型結構 | 兩層。第一層「基本面」：今晚預計陣容的球員實力＋球隊效率＋賽程疲勞，算分差。第二層「對照盤口」：輸入第一層分差與預測當下可得的盤口，輸出最終分差與機率 |
| 評分 | CLV、讓分回測 ROI、機率校準；猜中率只當參考 |
| 驗證 | walk-forward，依季切分；每次訓練產出特徵重要性報告 |
| 候選模型 | Ridge、HGB，加上深度學習，同一套規則比賽，贏的上線 |
| 歷史資料 | 回補 2015-16 到 2022-23 共 8 季，加上現有 3 季共 11 季；近期加權；2019-20（泡泡，無主場）與 2020-21（觀眾受限）特別標記 |
| 重訓頻率 | 維持每週一次 |
| 資料先於數據 | 先補齊資料、做品質檢查，再算特徵、訓練模型 |
| 逐回合紀錄 | 補資料時一次抓齊存檔；出手位置在 P4 用；on/off 在 P7 用，不重抓 |

## 6. 專案順序

每個專案開工前都要寫自己的設計文件，並經使用者同意。

**P0（進行中，另一個 session）靜態網站。** 與下列專案獨立，可並行。

**P1 恢復每日資料**
- 把 ESPN 抓取接進 `run_daily`，取代被擋的 `ingest_games`／`ingest_stats`；重新啟用 `daily_nba`。
- `NBA_SEASON` 預設值仍是 `2025-26`（`daily_nba.yml`），要改成 2026-27 並確認季初（各隊比賽數很少時）特徵與預測的行為。
- **立刻開始存傷兵快照、球隊名單快照、盤口快照**。這三樣無法事後回補，越早開始越好。
  - 現行 `injury_snapshots` 以 `(snapshot_date_et, source, team_abbr, player_name)` upsert（`jobs/snapshot_injuries.py:24`），同一天後抓的會覆蓋先抓的。若要保留一天內多個時間點，需另開只新增的新表（CLAUDE.md 不允許改舊表唯一鍵）。抓取時間點見 §7。
  - 盤口快照要有真實的抓取時間，最好同時有開盤與接近開賽的盤。
- 確認 GitHub Actions secrets 指向 Project2：DB 相關 secrets 最後更新於 2026-06-17，與 Project2 資料開始的時間（傷兵 06-17、預測 06-18）吻合，但這只是旁證，要跑一次唯讀的 `v2_diagnose` 才算驗證（需使用者同意觸發）。
- Odds API：repo 沒有設定任何 Actions variables，所以 `USE_ODDS` 走預設值 `0`，目前沒在用；`ODDS_API_KEY` secret 存在（最後更新 2026-02-22），是否仍有效、額度多少未驗證，在 P1 設計時確認。
- **下注時間點（使用者決定）**：使用者在**台北時間晚上**看網站、下注。台北晚上約等於美東當天早上，距離開賽（美東 19:00 起，約台北隔天 07:00，夏令時間結束後 08:00）大約 8 到 13 小時，西岸晚場更久。因此：
  - 「預測當下」= 台北傍晚。現有 10:30 UTC（台北 18:30）的排程正好在這之前跑完，作為正式預測與推薦的時間點；傷兵、名單、盤口快照都在這次一起抓。（時間點細節是設計者的決定，P1 可微調）
  - 另在接近開賽時再抓盤口，作為 CLV 的「收盤」基準，只用來評分，不回頭改晚上的推薦。現有 22:00 UTC（台北 06:00）的排程只接近東岸早場；西岸晚場（美東 22:00 開打）此時離開賽仍有數小時，P1 要決定是否依各場開賽時間多抓幾次。
  - 晚上下注時，出賽成疑（GTD）的球員通常還沒定案，模型要能處理「可能缺陣」，不能假設已知最終名單。NBA 傷兵報告的提交時限（一般認為是賽前一天傍晚，之後再更新）**未驗證**，P1 設計時確認。
- **Legacy 流程（使用者決定）**：P1 停掉 legacy 步驟的排程觸發（`preload` 等），程式碼保留不刪，避免每天因 stats.nba.com 被擋而亮紅燈、遮住 v2 的真實狀態。
- **防止 60 天停用（使用者同意做法）**：新增一個每月執行的小 workflow，用 GitHub API 重新啟用 `daily_nba`，不 commit、不 push。實際加入與啟用時仍需使用者當下同意。資料庫閒置暫停則靠每日排程本身避免（休賽期排程照跑即可）。
- P1 期間現行模型照舊運作（每日預測、週一重訓，啟用仍受 gates 把關），網站維持現有警語；它在讓分盤贏不了盤口的事實，由 P5、P6 處理。（設計者的決定）
- P1 從 `main` 開分支，不依賴 P0 是否已合併。（設計者的決定）
- 執行權限：設計文件獲批**不等於**同意任何操作。push、啟用 workflow、對正式 DB 跑 migration、觸發 workflow，每一項都依 CLAUDE.md 在當下個別取得使用者同意。

**P2 補資料**
- 回補 8 季的比賽、球隊與球員 box score、先發、沒上場與原因、裁判、盤口。
- 補齊現有缺漏的 box score。
- 逐回合紀錄抓取並存成 Parquet；決定存放位置。

**P3 資料品質檢查**
- 球員得分加總等於球隊得分、上場時間合計約 240 分鐘（含延長賽）、無漏場與重複、隊名正規化。
- 查清多出的第 1,231 場、ESPN 舊盤口的時間點（開盤、收盤或其他）。
- 盤口時間點的結論決定第二層能否用歷史資料訓練。

**P4 特徵 v1**
- 新增：投籃結構（三分出手比例等）、球員進階數據（TS%、使用率等）、出手位置分布、裁判、戰意（季末排名差）、客場連戰／跨時區／高海拔；四要素拆成攻、守兩組（目前是合併的淨值）。
- 第一層的「預計陣容」：歷史用 box score 的實際上場名單與沒上場原因還原；即時用傷兵與名單快照。
- 每項新特徵都要通過無洩漏測試，並在 walk-forward 證明有用才保留。

**P5 模型 v2**：兩層結構、新評分、深度學習候選、近期加權。

**P6 網站推薦**：最低可接受賠率、今天不建議、誠實戰績、串關助手。

**P7 on/off**：從 P2 存好的逐回合檔案推算場上五人，計算 on/off（需要正規化處理，例如 RAPM）。
