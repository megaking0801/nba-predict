# P6 網站：在「沒有可證明的優勢」下，誠實又有用

日期：2026-10-26
狀態：草稿（支線 Opus 撰寫，待主線審；產品方向待使用者選擇，見 `docs/handoff/2026-10-26-product-options.md`）
上層文件：`docs/superpowers/specs/2026-10-23-roadmap-design.md` §1、§2、§5、§6 P6；P5 結論見 `docs/handoff/2026-10-23-roadmap.md`
範圍：只定網站內容與驗證方式。不改程式；實作前另寫計畫（設計＋計畫經主線與支線互審）。

## 1. 前提（已測量，不是意見）

- 以 ESPN 公開 box score 衍生的資料，**找不到盤口沒反映的資訊**：fs1 ridge 在同一批場次上比近似收盤讓分線差 0.358 分 MAE（99% 區間 +0.279～+0.440，11 季全輸）；最簡單的第二層殘差學習者系統性更差（+0.022 分 MAE，7/7 調參季變差，β = −0.18）；P4 的十一個特徵候選沒有任何一個達標。過盤機率的校準斜率約 −0.03（模型的「過盤機率」沒有資訊），ATS 命中率約 49.9%，各 edge 門檻的 ROI 都是負的。
- 所以**「出手推薦」與「台彩最低可接受賠率」的前提不成立**：最低可接受賠率是為了「有優勢時，賠率高於多少才值得買」，沒有優勢就沒有這個東西可算。
- 使用者的原始需求（總體規劃 §1）：每天知道每場誰贏、勝率、讓分、大小分；單場／串關怎麼買、哪場值得買；誠實戰績；機率校準紀錄；勝率與可靠度分開。**其中「哪場值得買」現在的誠實答案是「沒有證據顯示有」**。網站應該把這個答案當成產品的一部分，而不是藏起來。
- 現有站（`webui/render.py`）的誠實度檢查（我讀程式的結果）：
  - 勝負卡：顯示模型勝率與「看好 X 勝」，並有「高命中率不等於獲利」的說明。模型勝負命中率 65.6%（主線 2026-10-26 的 `jobs.evaluate`）略高於純 Elo 的 65.2%。
  - **讓分卡：顯示「過盤機率 %」與「看好 X 破受讓盤」。這是目前最不誠實的元素**：過盤機率的校準斜率約 −0.03、ATS 命中約 50%，等於沒有資訊，卻以百分比和「看好」呈現。
  - 大小分卡：已是「估計優先」並附警語，方向保留為弱傾向（CLAUDE.md 已規定）。
  - 戰績區：已有「≠ 獲利」的揭露。

## 2. 需求對照

| 使用者需求 | P6 的處理 |
| :- | :- |
| 每場誰贏、勝率 | 保留。主要機率來源由 P6.0 的量測決定（§3.1）：預期是「盤口反推勝率」，模型勝率作為並列的第二個數字 |
| 勝率與「可靠度」分開 | 做，但「可靠度」定義為**資料完整度**（§3.5），不是準確度，也不是勝率的換句話說 |
| 讓分、大小分 | 顯示盤口與「模型估計 vs 盤口」的差；**移除過盤機率 % 與「看好破盤」**（§3.2） |
| 模型 vs 盤口 | 新增面板：逐季 MAE 對照、模型是否曾勝過盤口（沒有）、今日分歧最大的場次（標註「分歧不等於優勢」）（§3.3） |
| 機率校準紀錄 | 做（§3.4）：顯示機率分箱的實際頻率；歷史用 walk-forward，上線後另列即時紀錄 |
| 串關過關機率計算器 | 做（§3.6）：只算機率、期望值與每關損益兩平門檻，**不推薦** |
| 「今天沒有達到出手門檻的場次」 | 改成固定的誠實區塊「今天沒有推薦」（§3.7），附原因 |
| 台彩最低可接受賠率 | **不做**（前提不成立）。若日後出現證據（§7），再依總體規劃重啟 |

## 3. 內容設計

### 3.1 主要機率：盤口反推勝率 vs 模型勝率
- 事實：盤口在同批場次上的 MAE（整體 10.18）低於 fs1 ridge（10.63）。若模型的分差估計比盤口差，模型的勝率估計也應該比盤口反推的差；但這是推論，**要量**。
- P6.0 量測（唯讀，新報表 `jobs.market_layer --report winprob`）：
  1. 把盤口讓分換成勝率：對主隊勝負 `y` 做 `y ~ home_spread` 的邏輯斯迴歸，**用 expanding-window（只用該場以前的賽季）**擬合，得到 `p_line`。
  2. 與模型的 `p_model = Φ(mu/σ)`（`jobs/model.py` 既有邏輯，walk-forward 的 `mu`、`sigma`）在同一批場次上比 Brier、log-loss、勝負命中率、校準斜率，逐季，含配對區塊 bootstrap 的 99% 區間。
  3. 決定規則（事前登記）：若 `p_line` 的 Brier 優於 `p_model` 且 99% 區間不含 0，網站的**主要勝率**用 `p_line`（標註「由盤口反推」），模型勝率改為並列的第二個數字；否則兩者並列、不分主次。
- 沒有盤口的場次（preseason、少數 regular）：只顯示模型勝率，並標註「無盤口可比較」。
- 注意：歷史勝負盤口價格多為預設值（P5 設計 §2.1），所以**勝率反推只用讓分線，不用價格**。

### 3.2 每場卡片
- 勝負卡：兩個數字並列（盤口反推／模型），其餘維持。「看好 X 勝」改為「勝率較高：X」，避免推薦語氣。
- 讓分卡：顯示盤口（沿用）、**模型估計分差與盤口的差**（例如「模型比盤口多給主隊 1.2 分」），並加固定註記：「11 個完整球季的 walk-forward 驗證中，模型的分差誤差比盤口大約 0.36 分，沒有任何一季比盤口準」。移除過盤機率 %、移除「看好破受讓盤」、移除命中徽章（命中徽章保留給已結算的紀錄區，不再對讓分「看好」計命中）。
- 大小分卡：維持現狀（估計優先、方向為弱傾向、附警語）。
- 結果顯示（賽後）：保留比分與勝負命中（勝負）；讓分／大小分只顯示實際結果與盤口，不貼「命中／未中」。

### 3.3 模型 vs 盤口 面板
- 表：逐季「盤口 MAE」「模型 MAE」「差」（P5.0 的 `line_by_season` 與 `ridge_minus_line` 逐季）。
- 一句話結論（固定文案）：「11 個完整球季中，模型沒有任何一季比盤口準。」（以資料為準；若日後改變就自動隨資料更新，而不是寫死文字。2026-27 目前只有 11 場，不列入。）
- 今日分歧：列出模型與盤口分歧最大的前 3 場，標題為「模型與盤口分歧」，副註「歷史上這類分歧沒有帶來獲利：ATS 命中約 49.9%」。不稱為推薦、不排序成「最佳選擇」。

### 3.4 校準紀錄
- 圖／表：把顯示給使用者的機率（P6.0 決定的主要勝率）分成 10 箱，列每箱的場次數與實際主隊勝率，附 99% 區間。歷史部分用 walk-forward 預測（不是 in-sample），明講。
- 即時紀錄：2026-10-24 起的預測，結算後逐日累積，與歷史並列；樣本少時標註「樣本不足」。
- 校準本身**不會產生優勢**（總體規劃 §5 已記），只是讓數字誠實；網站要這樣寫。

### 3.5 可靠度 = 資料完整度
定義為檢查清單，不是機率：
1. 有盤口且新（`LINE_MAX_AGE_HOURS` = 12 小時以內）；
2. 傷兵快照新（當日已抓）；
3. 兩隊本季已賽 ≥ 10 場（`games_played_min`）；
4. 模型與預測都存在、且不是休賽期舊模型；
5. 沒有「明星球員出賽成疑尚未定案」的情況（傷兵 veto 既有邏輯 `injury_veto_for`）。
顯示為「資料完整度：5 項中 4 項」與缺的項目。**文字明講它不代表準確度。**

### 3.6 串關計算器（互動，純前端）
- 輸入：使用者選 2～4 場、每場選一邊，並**自己輸入該關的十進位賠率**（台彩賠率我們不抓，總體規劃 §4.1）；每關的機率預設用 §3.1 的主要勝率（勝負）。讓分關：預設機率 0.5（盤口設在約 50%）並說明「模型的過盤機率沒有證據」，使用者可自行覆蓋。
- 輸出：
  - 過關機率 ＝ 各關機率相乘（**假設各關獨立**，並註明；同一場不同玩法不可同串）；
  - 期望值（每 1 元）＝ 過關機率 × 賠率乘積 − 1；
  - 每關損益兩平門檻：該關賠率 `o` 時要 `p ≥ 1/o`；串 n 關在各關同賠率下，要每關都達到 `1/o`，整體過關機率為 `(1/o)^n`；並列出例子（每關 1.75：每關要 57.1%，三關整體約 18.7%）。
  - 固定一句話：「串關的抽水逐關疊加；沒有優勢時，期望值是負的。」
- 技術：內嵌 JS（靜態站，無外部依賴）；公式同時在 Python 有一份對照實作，單元測試比對同一組輸入；實機行為用瀏覽器驗證（Claude in Chrome），不是只靠測試。
- 不做：任何形式的「建議串哪幾關」。台彩的串關規則（最少最多關數、同場限制、是否抽水以不同方式計算）我沒有查證，計算器只用數學，並註明「實際規則以台彩為準」。

### 3.7 「今天沒有推薦」
固定區塊，永遠顯示，內容：「本站不提供下注推薦：11 個完整球季的驗證顯示模型沒有勝過盤口（見『模型 vs 盤口』）。以下是每場的勝率與盤口，僅供參考與娛樂。」不使用「達到門檻／未達門檻」的說法（那暗示存在一個門檻之上的推薦）。

### 3.8 文案與定位
- 定位維持 CLAUDE.md：數據預測與娛樂，不是投注建議。
- 全站不出現：穩賺、明牌、推薦下注、最低可接受賠率（作為行動建議）。
- 「猜中率」沿用，但同頁並列「盤口反推的猜中率」（P6.0 量測）作對照，避免讓 65% 看起來很厲害。

## 4. 技術與驗證
- 變更面：`webui/render.py`（卡片、面板、串關計算器）、`webui/queries.py`（只增 SELECT：逐季盤口 vs 模型表、校準箱、完整度所需欄位）、`webui/build_site.py`（新頁／區塊）、`jobs/market_layer.py`（`winprob` 報表）。**不改** `jobs/` 的特徵、模型、picks、gates。
- 整頁 golden（`tests/test_streamlit_golden.py`）會因此改變：這是**刻意的行為變更**，golden 更新要在 commit 說明（CLAUDE.md 規則）；新元素另加單元測試。
- `render.py` 規則不變：不 import streamlit、DB 來的文字一律 `esc()`。
- 串關計算器的 JS 與 Python 對照測試；瀏覽器實測（載入、輸入、邊界值如賠率 1.0、機率 0 與 1、空選擇）。
- 資料新鮮度與過期提示沿用既有 `STALE_HOURS` 等機制。

## 6. 風險與未驗證
- 「盤口反推勝率比模型好」尚未量測，只是推論；P6.0 的結果可能是兩者無差異。
- 台彩的賠率、串關規則與抽水**沒有查證**；計算器不依賴它們，但文案不可暗示。
- 校準箱在樣本少的箱子區間會很寬，圖要顯示區間，避免過度解讀。
- 即時紀錄樣本從 2026-10-24 起累積，初期不足以下結論。
- 網站使用者是自己和朋友（總體規劃 §5）；文案調整的語氣由使用者決定。

## 7. 重啟「推薦」的條件（事先寫好，避免日後被說服）
需同時成立：(a) 歷史上有通過 P5 §4 保留規則的第二層（目前沒有）；(b) 即時快照上 CLV 為正且樣本足夠（至少約 660 次出手的量級，見 P5 §6；目前 n = 8 場）；(c) 使用者決定。在此之前，網站不出現推薦。
