# 玩法搜尋：有沒有任何玩法在回測有正期望值

日期：2026-10-26
狀態：草稿（支線 Opus 撰寫，待主線審）
背景：使用者的目標是賺錢，要求「找一種回測有賺錢的玩法，不限受讓」，並看到回測勝率約六成。P5 已證明讓分盤上模型沒有勝過盤口。這份文件回答剩下的問題：**換一種玩法（不讓分、大小分、串關）有沒有正期望值**，規則事前登記，結論照實報告。

## 1. 先講「六成勝率」是什麼（已量測）
- 主線的量測：盤口讓分的熱門方（近似收盤線）例行賽勝率 67.94%（n=13,173）、季後賽 66.45%；0–3 分 53.8%、3–6 分 61.7%、6–9 分 72.6%、9–12 分 79.4%、12+ 分 89.1%。我們的模型猜勝負 65.6%，比「單純押熱門」還低。
- 獲利取決於「勝率 × 賠率」，不是勝率。押熱門的期望值 = `p·o − 1`；賠率 `o` 已經反映熱門的勝率，所以長期期望值約等於 −抽水。**勝率高 = 賠率低**，不等於賺錢。這點要用資料展示（§5 的基準策略），不只是講道理。

## 2. 資料：ESPN core odds 的不讓分（moneyline）
2026-10-26 以只讀 GET 抽樣 11 個日期（每個日期第一場），結果：
- **所有抽到的球季都有 moneyline**：2015-16 起每場 7–16 個供應商（5Dimes、BetOnline、Westgate、Caesars、Betfair 等），2024-25 只剩 2 個、2025-26 起只有 1 個（DraftKings）。
- 格式有兩種：舊格式只有 `current` 區塊與頂層 `moneyLine` 整數（美式賠率），新格式（2023-24 起抽到）有 `open`／`close`／`current` 區塊，內含 `american` 與 `decimal`。
- **陷阱**：(a) 供應商名單含「Live Odds」（例如 `Caesars (New Jersey) - Live Odds`，1300／−3200 是比賽中的賠率），必須排除；(b) `consensus` 沒有 moneyline、`Opening` 是開盤價；(c) 舊格式的 `current` 抓取時間未知，不能保證是開賽前最後一筆；(d) 2024-25 起只有單一供應商，跨年代的價格水準可能不同。
- **意外的發現（影響先前的結論）**：同一份資料裡，**讓分的價格（`spreadOdds`）在舊格式是有的**（例如 −118／−102），但現有 `parse_close_line` 只讀區塊內的 `spread.decimal`，舊格式沒有 decimal 欄位，所以才退回預設 1.91——也就是 P5 設計 §2.1 說「前 8 季價格全是預設值」是**解析器的缺陷，不是 ESPN 沒給**。這使歷史讓分／大小分的價格（和去水機率）其實可以救回，需要修 `parse_close_line` 並重抓（會寫正式 DB，要使用者同意；本設計不做）。本設計的玩法回測改用本機檔案，不依賴 DB 裡的價格欄位。

## 3. 供應商與價格選擇（事前登記）
每場比賽的合格供應商：名稱不含 `live`（不分大小寫）、不是 `consensus`／`Opening`、兩邊 moneyline 都有且非 0、十進位賠率落在 [1.01, 15]。價格取 `close` → `current` → `open` → 頂層 `moneyLine`（第一個存在的）。
- **市場機率** `p_market` ＝ 各合格供應商「去水後主隊機率」的中位數。
- **下注價格（主要）** ＝ 各合格供應商該邊十進位賠率的中位數（代表一般書商）。
- **下注價格（上界，只作參考）** ＝ 最佳賠率（多家比價；使用者在台灣拿不到）。
- 合格供應商 0 家的比賽不納入並計數。

## 4. 候選與規則
### (i) 不讓分（moneyline）
- 模型勝率 `p_model = Φ(mu/σ)`（fs1 ridge 的 walk-forward 預測，與 P4／P5 同一條管線；**模型不使用任何賠率**）。
- **基準策略（不用模型，展示抽水）**：永遠押熱門（`p_market` 高的一邊）、永遠押冥門、永遠押主隊、永遠押客隊；各用中位數價格，逐季與全期 ROI。
- **模型策略**：`p_model − p_market ≥ e` 押主隊、`≤ −e` 押客隊，`e ∈ {0.02, 0.04, 0.06}`（只有這三個門檻，事前固定）；每注 1 單位，ROI ＝ 總損益 ÷ 注數，用該場的中位數價格結算（價格已含抽水，不另扣）。
- 通過條件（全部成立才算「回測有正期望值」）：某個 `e` 的 ROI 的 99.2% 區間（Bonferroni：三個門檻）下界 > 0；注數 ≥ 1,000；逐季至少 2/3 的季 ROI > 0。
- 區間：以 14 天為區塊的 bootstrap（相鄰比賽相關），2,000 次、固定種子。

### (ii) 大小分
- 資料：`v_closing_lines` 的 `total_line`，排除 P3 E4 的壞值（<170 或 >280）；價格：DB 裡的 `over_price`／`under_price` 在舊季多為預設 1.91（§2），所以**主要結果以 −110（十進位 1.909）結算**，並另外以台彩估算 1.75 結算（使用者提供的估算，未驗證）。
- 模型：totals 模型（`TOTAL_FEATURE_NAMES`，walk-forward）；方向 ＝ 模型總分減盤口總分，絕對差 `g ∈ {1, 2, 3}` 分以上才下注。
- 基準策略：永遠押大、永遠押小。
- 通過條件同 (i)。先驗：CLAUDE.md 已記錄方向命中率約 48%，預期不通過。

### (iii) 串關
各關相乘，只有在單關有正期望值時才有意義，**不另測**。若 (i) 或 (ii) 通過，再以同一批注單模擬 2–3 關串關（獨立假設，同日不同場）。

### (iv) 其他玩法（半場、球員 props、單節）
沒有資料，列為「無資料可測」。

## 5. 要回答使用者的幾個具體問題（輸出）
1. 押熱門的勝率與 ROI 是多少（逐季）？（預期：勝率約 67%、ROI 約為負的抽水。）
2. 模型勝率 vs 市場機率：模型有沒有任何一個 edge 門檻 ROI 為正？
3. 大小分同上。
4. 如果完全沒有玩法通過：直接說「回測沒有任何玩法有正期望值」，並指出 §2 的資料限制（沒有台彩賠率、2024-25 起單一供應商）。

## 6. 實作與指令
`jobs/playbook.py`（唯讀；只對 ESPN 做 GET、對 DB 只 SELECT）：
- `python -m jobs.playbook fetch --out <本機檔案> [--seasons 2023-24,...] [--limit N]`：從 DB 讀 final 比賽的 id，逐場 GET `odds`，每場把解析後的合格欄位（供應商、moneyline、讓分價、總分價）寫成一行 JSONL；可續跑（略過已有的 id）；每次請求間隔 ≥ 0.15 秒；輸出檔案放 repo 外或 `.gitignore` 的 `data_local/`。約 1.4 萬場，時間約一小時量級（**估計**）。
- `python -m jobs.playbook moneyline --in <檔案> --out <json>`：§4(i) 的基準與模型策略。
- `python -m jobs.playbook totals --out <json>`：§4(ii)。
測試：解析函式用 2015-16 與 2023-24 兩種格式的實際 JSON 樣本（縮小後存在 `tests/fixtures/`）；ROI 與 bootstrap 用合成資料驗證（已知賠率與勝率的期望值）。

## 7. 風險與未驗證
- 舊格式 `current` 的時間點未知；若它是比賽進行中或賽後的價格，ROI 會失真（以「合格供應商」規則與 `Live` 排除降低，但無法完全排除）。
- 價格中位數代表「一般書商」，不是台彩；台彩的不讓分賠率、抽水結構沒有資料。
- 2024-25 起單一供應商，樣本內的價格水準與前期可能不同；逐季報告可看出。
- 一個通過的結果仍需要在即時快照（2026-10-24 起）上重現才有資格談實際下注；回測的 ROI 通過不是獲利保證。
- Bonferroni 只校正三個門檻，沒有校正「換了幾種玩法」；若多個玩法各自測，結論以更嚴格的 99.5% 區間解讀。
